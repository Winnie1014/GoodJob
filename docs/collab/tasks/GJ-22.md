## 背景

Owner 询问 GoodJob 仓库能否改为 public，要求先核查是否有需要脱敏的内容。这**不是** [验收基线 §6 发布条件](../../40-delivery/acceptance-baseline.md)的 6 条之一——那 6 条门的是"能否创建/更新可安装私有版本"，与"仓库本身能否公开可见"是两个独立问题，只有条件 5（仓库无个人数据/扫描缓存/密钥/真实项目源码副本）与本卡直接相关，其余 5 条不适用、不构成本卡阻塞。

Architect 已做过一轮**机械扫描**（全历史、全分支，非仅当前 `main` 或工作树），方法与结论见派卡信道消息，此处不复述。**尚未完成的是叙事类长文档的通读**（`channel.md` 现已超过 3300 行、`backlog.md`、`acceptance-evidence.md`、全部任务卡、ADR、`opus-review.md`）——机械正则扫描抓不住"一段话是否语义上泄漏了超出 GoodJob 项目自身开发过程范围的真实内容"，这类判断需要人读。这是本卡的重点交付。

## 目标

产出一份结构化审计报告，逐维度回答"如果这个仓库现在改为 public，会暴露什么"，覆盖**全部 git 历史（所有 commit、所有本地与远程分支/ref），不只是当前 `main` 的工作树快照**——已被删除的敏感内容只要仍在历史里就会随公开而暴露。报告面向 Owner 的开源决策，但**本卡不做开源决策本身，也不执行任何修复**（无论是未来 `.gitignore` 调整还是历史改写）——发现问题只报告，处置留给后续裁决。

## 涉及范围

- **只读输入**：GoodJob 仓库自身的完整 git 历史（`git rev-list --all` 可达的全部对象）与当前工作树；不限于 `main`。
- **禁止**：
  - 读取或触碰 CodeRoute、SliverShield 或任何仓库外的真实工作区——与本卡审计对象无关，不在范围内；
  - 修改仓库任何现有文件、执行任何 `git filter-branch`/`git filter-repo`/交互式 rebase 等历史改写操作、修改 GitHub 仓库可见性或任何账号设置——本卡是纯只读审计，处置权不在本卡；
  - **把发现的敏感内容原文写入交付文档或信道**——审计报告与信道消息本身也活在这个即将可能公开的仓库里，若把发现的密钥片段/真实姓名上下文/真实电话号码等原样抄进报告，等于制造了第二份泄漏源。发现类内容一律只报告**类别 + 定位（commit hash + 文件路径 + 行号）+ 严重度**，不贴原文；复核者按定位自行在本地查看。
- **允许写入**：新增 `docs/40-delivery/open-source-desensitization-audit.md`；`docs/collab/channel.md` 物理 EOF 追加协作消息（元协议豁免）。

## 接口契约

**契约 1 — 六个审计维度，逐一给结论，不得合并跳过：**

1. **密钥/凭据类**：私钥头（`BEGIN ... PRIVATE KEY`）、云服务 AccessKey/Token 格式（AWS/GitHub/Slack 等）、通用 `password=`/`secret=`/`token=` 赋值模式、敏感文件名（`.env`/`credentials*`/`id_rsa`/`*.pem`/`*.key`/`*.p12`/`*.pfx`/`*.sqlite3` 等）是否曾在任意 commit 中出现过（即使当前已删除）；
2. **PII 类**：真实姓名、邮箱、电话、地址等——**必须包含 git commit 的 author/committer 元数据**，不能只查文件内容（元数据不经 `git grep` 文件内容扫描可见，需要 `git log --format`）；
3. **真实扫描内容泄漏类**：CodeRoute/SliverShield 的真实源码、真实 JD 文本、Owner 对 context cards 的回答原文是否曾经进入过 GoodJob 仓库本身——这正是[验收基线 §6 条件 5](../../40-delivery/acceptance-baseline.md)与多张既有任务卡（GJ-14/16A/16B）反复强调的边界，本卡独立复核一次而非信任既有卡的自述；
4. **叙事类文档语义泄漏**（本卡重点，机械正则抓不住）：通读 `channel.md`、`backlog.md`、`docs/40-delivery/acceptance-evidence.md`、`docs/collab/tasks/*.md`、`docs/30-decisions/adrs/*.md`、`opus-review.md`、`README.md`、`docs/index.md`，核查是否存在超出"GoodJob 项目自身开发过程"范围的真实内容：真实公司名、真实简历/JD 原文、疑似真实生产代码片段（而非示意/伪代码）、Owner 真实身份的额外线索；
5. **全部分支/ref**：不只查 `main`，本地与 `remotes/origin/*` 的每个分支都要检查是否携带 `main` 没有的内容（已合并的分支其内容已包含在 `main` 历史中，仍需确认；未合并的分支需要单独审计其独有 diff）；
6. **前瞻性检查**：`.gitignore` 覆盖是否足够防止未来误提交（缓存目录、`.venv`、构建产物、临时 data directory 等），这不是历史问题但决定"开源之后还会不会出问题"。

**契约 2 — 不得只信任 Architect 已披露的机械扫描结论。** 派卡消息会披露 Architect 对维度 1/2/3/5/6 的初步方法与结果，**这是线索,不是结论**——按 [anti-patterns.md](../anti-patterns.md)"拿未经自证的一次性探针打回实现"的对称版本（这里是"不经自证就采信一次性探针的清白结论"同样危险），交付报告须对至少维度 1（密钥/凭据）与维度 2（PII）独立重新执行检查，不能只复述 Architect 的数字。维度 4（叙事类通读）是 Architect 尚未做的部分，全部工作量在本卡。

**契约 3 — 严重度分级，仿 L 分级但独立于实施发现分级：**

- 🔴 **阻断级**：真实密钥/凭据、可定位到具体自然人的 PII（含仓库外第三方，如 Owner 的合作方/前雇主）、真实公司专有代码——开源前必须处置；
- 🟡 **建议级**：非阻断但建议改善的内容（如可以接受但值得注意的元数据暴露）；
- ⚪ **已核查确认干净**：检查过、无发现的维度，必须列出以证明覆盖到了，不是漏检。

**契约 3 附则（[#114](../channel.md) L1 → 裁决新增，2026-08-11）**：Owner 本人的身份标识若经 Owner 在信道外明确裁定同意作为本项目公开署名，则**该身份**不计入阻断级，归入⚪已核查确认干净，但报告仍须点名其出现范围（全部 git author/committer 元数据 + 具体文档定位）并注明"经 Owner 2026-08-11 裁定同意公开"，不得因为这条例外就跳过维度 2 检查本身或省略披露。**该例外只适用于 Owner 已明确裁定的这一个身份**（`lc.jin <lc.jin@invo.cn>`）——审计中若发现任何其他可定位自然人的 PII（含 Owner 的其他未裁定身份、任何第三方），仍按原判据走 🔴，Implementer 不得援引本条自行扩大例外范围或自行判断"这个应该也算 Owner 同意"。

## DoD

**D1｜六维度逐条结论。** 契约 1 的六个维度每条都有：检查方法（命令或通读范围）、覆盖的 ref/commit 范围、结论（🔴/🟡/⚪）。

**D2｜全历史覆盖证明。** 报告点名实际检查过的 commit 总数与分支/ref 清单（`git rev-list --all | wc -l`、`git branch -a` 的完整输出），不得只声称"检查过"而不给可复核的范围证据。

**D3｜独立复核证明。** 维度 1、2 各自独立重新执行检查（不是转述 Architect 数字），交付报告贴出所用命令与得到的结果，与派卡消息中 Architect 的结论对照，一致或不一致均需说明。

**D4｜零原文泄漏。** 交付报告与相关信道消息中**不含**任何被发现的敏感内容原文（密钥片段、真实电话、真实姓名出现的完整上下文段落等）——只有类别 + 定位 + 严重度。这条本身要在交付时自证：说明如何确认没有夹带原文。

**D5｜明确的开源建议。** 报告结尾给出一个 `建议开源 / 有条件建议开源（列出前置条件） / 不建议开源（列出阻断项）` 三选一结论，供 Architect 终审参考——**不是最终决定**，本卡不裁决是否真的改为 public。

**D6｜叙事类通读的具体产出。** 契约 1 第 4 条不能只写"已通读，无发现"——每个文档给出实际读了多大范围（行数/章节）的证据，若有 🟡/🔴 发现按契约 3 的格式给出定位。

## 边界与禁区

- 不判断、不执行仓库可见性变更（GitHub 仓库设置由 Owner 或 Owner 明确指示后操作，不在本卡）；
- 不执行任何 git 历史改写操作；
- 不读取 CodeRoute、SliverShield 或本卡范围外的任何真实工作区；
- 若发现 🔴 阻断级问题，**立即 L1 上报**（不是等交付报告才说）——这类发现的处置涉及是否需要历史改写等高风险操作，必须 Architect 裁决,不能自行决定"要不要继续往下审"；**L1 消息同样受契约"涉及范围"零原文规则约束**——上报"发现了什么类别、在哪个定位"，不贴敏感内容原文，Architect 裁决时按定位自行本地核查；
- 若怀疑某发现但无法在不暴露原文的前提下证明，按 L2/L3 上报存疑，不因为"说不清楚"就不报。
