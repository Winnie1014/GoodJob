# Architect 手册(出卡 / 裁决 / 验收 / 收口)

> 前置阅读:[protocol.md](protocol.md)(共同协议)。本手册只写 Architect 侧的操作序列。
> 另两方的手册:[implementer.md](implementer.md) / [reviewer.md](reviewer.md)。
> 职责总纲:出任务卡、定契约、终审验收、merge、裁决、维护 backlog 与设计文档。
> 权力边界:**不替 Implementer 写实现**——唯一例外是两轮打回仍不过后的接管重写。

## 1. 出卡

### 1.1 前置检查

1. 从 backlog 定位任务,确认里程碑归属与优先级;
2. 重读对应设计文档章节(卡面"背景"必须给出章节指针,如 `xxx-design.md §2.1`);
3. 确认全部前置卡已合入主干(未合入则先收口或调整顺序);
4. 决定**单卡派还是批量派**:同一垂直切片且相互依赖 → 批量(统一分支、按卡独立 commit、统一交付统一验收);相互独立 → 单卡。

### 1.2 卡面撰写

模板:`templates/task-card-dev.md`(开发类)/ `templates/task-card-content.md`(内容生产类)。

必填项:状态行(领取状态/双方身份)、backlog 对应、前置任务、分支名、**验收强度**(protocol §2.2，附一句威胁模型理由)、**体量预授权**(预算 × 1.3 = gross 上限;穷举型声明不设限)、背景(带文档指针)、目标(可观察结果,不写实现)、涉及范围(允许/禁止,白名单式)、接口契约(Architect 给定,Implementer 不得擅改)、DoD(逐条可机器/人工检查)、边界与禁区、交付物。

### 1.3 出卡门禁(逐条自查,派卡消息中披露)

1. **体量预算乘法**:把强制交付面乘出来(N 个 schema/规则 × 正反测试 ≈ 行数量级),可预见超默认预算的在卡内预授权;
2. **新消费关系 dry-check**:卡面第一次消费某个基建(新包导入、新依赖边界、新构建路径)时,出卡前**实际验证该路径存在**(真的 import 一次),不把"应该能用"写进卡面;
3. **L1 同因扫描**:任何 L1 裁决落地时,当轮扫描同批其余卡是否同病,一次裁决全批修完——同一病因不允许卡第二轮;
4. **顺序/坐标数据源**:卡面引用的每个「顺序、坐标、默认值」必须有明确数据源——先沿数据链路(源文件 → 构建 → 运行时)确认该信息真实存在且可达;引用不存在的数据源是**出卡侧缺陷**;
5. **数据契约全字段对照**:卡面契约与 schema/类型定义逐字段对照过一遍,不凭记忆写契约;
6. **三区一致性**:涉及范围 ⇄ 接口契约 ⇄ 验收标准通读一遍,互相不矛盾;**任何修订/裁决落卡后必须重做本项**;
7. **依赖闭包**:点名技术栈时枚举官方 companion 闭包并核查 peerDependencies(protocol §8);
8. **派生量不写死**:契约/DoD 里出现计数、数量、度量(文件数、用例数、行数)时,写**计算方式**而非当次观测值。确需写值的,核对它在**卡面指定的基线**上仍成立——不是在你观测它的那个提交上。(源案例:GoodJob GJ-11,DoD 写死 `38 files`,而卡面指定基线正是把它变成 39 的那个提交);
   - **推论:卡面不写死基线 commit。** 写卡时可观测的 HEAD **必然早于卡面自身的落位提交**,于是卡面指定的基线里根本没有这张卡。基线一律由派卡消息给出(卡面写"基线由派卡消息指定"),这是唯一能让「卡面存在于其基线中」成立的写法。(源案例:GoodJob GJ-18,卡面写 `b6982a8`、派卡消息写 `18edb17`,而前者不含 GJ-18.md);
9. **枚举优先指向上游事实源**:卡面出现清单/命令表/名字表时,优先写"以 X 文档/X 代码为准"并给出核对方式,而不是手工抄一份。手工枚举必漏,且漏项不会被变异测试发现——它压根不在被测集合里。确需内联时,同时注明"以实际为准,发现不一致按 L2 报告"。(源案例:GoodJob GJ-07 契约 2 漏掉整个文档族)
10. **威胁模型自查**:按 protocol §2.2 回答“谁会攻击这段代码”。只处理仓库自身输入就是常规档；扫描 Owner 工作区、消费 JD、处理 capability/外部路径或渲染不可信数据就是对抗档。档位和理由写进卡面与 backlog，不留到验收时临场决定。
11. **前后对比类 DoD 必须固定语料**:凡是"修复前跑一次、修复后跑一次、比较差值"形态的 DoD,卡面必须写明**只变代码、不变语料**(同一 HEAD / 同一输入集,仅以变异或 checkout 切换被测实现)。只写"前后各一次"会让实现方在两个不同基线上各跑一次,差值里混入未控变量,证据强度归零而双方都看不出来。同时要求交付报告披露两次运行的语料标识(HEAD、输入根、采集时刻),否则验收方无从判断是否受控。(源案例:GoodJob GJ-18 D5,前后现场 `head_commit` 分别为 `18edb17` 与 `bbec1b1`,结论正确但过程未受控,信道 #89)

### 1.4 派卡序列

写卡 →〔高风险卡:送 Reviewer 预审([protocol §2.1](protocol.md),一轮止损)→ 按预审结论修订 → 三区一致性重做〕→ backlog 标注 → commit 主干(`docs: 出 <ID> 任务卡 (<署名>)`) → 信道派卡消息 → 自己的消息不 add。形态 A 无需 push;形态 B 必须 push 后才算派出。

**什么算高风险卡**:新契约面 / 跨模块 / 首次消费某基建 / 批量卡 / 对抗档卡 / **卡面里含未验证断言**。最后一类最容易漏——若你在写卡过程中更正过自己先前的某个断言,这张卡就该送审(源案例:GJ-19,卡面更正了 #71/#73 对 `_is_sensitive` 结构的描述,送审后被查出四项,信道 #81)。

派卡消息要素:卡面路径、分支名、单卡/批量说明、**出卡门禁自查披露**(数据面是否就绪、契约变更面、新依赖面)、期望的交付消息编号。

## 2. 信道处理

**第 0 步永远是**:`git add <信道文件>` 对对方消息作已读回执(形态 B 先 pull),然后按消息类型分流:

| 消息类型 | 处理 |
| --- | --- |
| L1 裁决请求 | 走 §3 裁决流程,即时处理(对方在停工等待);**裁决必须抄送 Reviewer**([protocol §5](protocol.md))——她没收到就会按旧卡面初审 |
| 卡面预审结论 | 逐条定性(采纳→改卡;否决→给理由),改完重做三区一致性,然后派卡。**一轮止损,不再送审** |
| 初审结论(放行) | 走 §4 验收五步,**全量,不因初审放行而精简** |
| 初审结论(升级) | Reviewer 指不到卡面依据 → 是卡面或裁决本身的问题,由你裁决 |
| 交付报告 | 走 §4 验收五步 |
| 技术问答 | 直接信道回复 |
| L2/L3(随交付) | 验收时逐条定性,不允许无回应合并 |

## 3. 裁决流程(L1)

1. 读全上下文:报告原文、涉及文档、相关代码——不凭卡面记忆裁决;
2. 对比 Implementer 的建议方案(若有),裁决结论与理由写清;
3. 信道回复裁决:结论 / 理由 / 需要落卡的修改 / 复工指令;
4. **同因扫描**:同批其余卡是否同病,一次修完;
5. 落卡后**三区通读**(范围 ⇄ 契约 ⇄ DoD)再放行复工——裁决改了契约却没同步范围,是制造新矛盾的典型事故。

L2/L3 定性归宿:采纳 → 改设计文档 / 开新任务 / backlog 挂账(机动池或前置决策);否决 → 信道给理由。**每一条都要有归宿,挂账必须落到 backlog 可见位置**。

## 4. 验收五步

> 触发:收到交付报告(部署 Reviewer 时,通常是收到她的放行结论)。逐卡执行,批量交付统一验收。
>
> **终审不因初审放行而精简。**初审台账是交叉参照与责任定位用的,不替代任何一步。本项目 Reviewer 与 Implementer 同源([protocol §1.2](protocol.md)),初审对她的直觉盲区覆盖有限——这正是终审必须全量重跑的原因。**复核 Reviewer 复核过的东西时,尤其要问一句她的核查方式本身有没有盲点**(源案例:GJ-18 终审,初审与交付方读同两份实测现场,一起漏掉了语料未受控,信道 #89)。

**第 0 步：确认卡面验收强度。**常规档按常规档验，不得在交付后临时追加对抗要求；对抗档必须逐项覆盖卡面声明的恶意输入、边界绕过和失败关闭场景。若发现出卡时定档错误，记为出卡侧 L2，并在后续卡修正，不以此偷换当前卡契约。

1. **体量审计**:找出分支全部提交 → `git log --numstat` 按格式化后口径统计 → 对照卡面预算;超量看披露是否成立(强制交付面撑出来的成立,夹带的不成立)。
2. **代码 review**(逐卡):
   - DoD 逐条核对,契约与 shared 类型完全一致;
   - 「自主决策」节逐项审计绿区四条件与证据,越界未停工按铁律违规处理;
   - **L1 裁决落地忠实性**:此前每个裁决是否被按裁决原文实现;
   - 边界安全:超时 / 错误路径 / 双平台差异 / 资源清理(进程、临时目录、句柄);
   - 简化机会(AI 代码常见过度封装)与回归风险(是否影响范围外行为);
   - **定性纪律**:发现疑似缺陷,先沿数据链路核查是不是**出卡侧引用了不存在的数据源**,再定实现侧责任——不冤枉实现者;出卡侧缺陷如实自记并进反模式池。
3. **本地门禁复跑**:项目门禁命令表全量跑一遍,不轻信报告里的"全绿";生成物按固定命令重生成 + hash 比对零漂移。
   - 临时验证探针在用于判定实现缺陷前，必须先用已知干净样本证明不会假红，再注入一个已知缺陷证明不会假绿；未经自证的一次性脚本只能作为线索，不能作为打回依据。
4. **CI 核实**:全部 run success 且指向同一 HEAD(形态 B 看远端分支;形态 A 看共享工作区当前提交)。
5. **运行验证**:关键路径真机跑一遍;UI 类核对截图(动画类抓中间帧证明真实运动);必要时请 Owner 亲手体验再收口。

**实施发现逐条处理**(protocol §5 义务)后,信道回复验收结论:复核证据(五步各自结果)/ 发现逐条定性 / 收口安排。

**打回**:批注逐条、最多两轮;仍不过则接管重写(信道声明接管,不静默动手)。

## 5. 收口序列

1. **确认对方无未提交现场**(形态 A 必须——merge/切分支会摧毁对方工作区;形态 B 确认远端分支即终态);
2. 信道验收记录 commit(已读例外,protocol §3);
3. `git merge --no-ff <分支>`(消息:`merge: <批名/卡名> 验收合入`);
4. backlog 更新:完成卡标 ✅ + 裁决引注(可追溯到信道编号);新挂账落机动池/前置决策区;
5. 主干冒烟(门禁快速子集,证明合并态健康);
6. push(收口按项目惯例;其余时刻只按 Owner 明确要求);
7. 删分支(远端 + 本地;若本地分支比远端多信道类提交,先 `git merge-base --is-ancestor <提交> main` 确认已含于主干再强删);
8. 信道收口通知:merge hash / backlog 更新 / 分支清理 / 里程碑状态 / 下批候选。

## 6. 文档治理

- backlog 是任务状态唯一事实源;裁决产出落 ADR 或设计文档,卡面只引用;
- 教训进 anti-patterns.md(项目实例先记,定期回流 skill 母本);
- 出卡门禁清单是活文档:每次出卡侧缺陷定性后,把新检查项追加进 §1.3。
