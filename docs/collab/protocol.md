# 共同协议(Common Protocol)

> 本文件是多 agent 协作的共同底座,Architect、Implementer 与 Reviewer 都必须完整遵守。
> 角色专属操作手册:[architect.md](architect.md) / [implementer.md](implementer.md) / [reviewer.md](reviewer.md)。
> 历史教训:[anti-patterns.md](anti-patterns.md)。本协议源自 CodeRoute 项目协作规范 v1.5 及其实践演化。
>
> **GoodJob 实例说明**:本文件是协作运行区文档,不是产品契约。产品与架构契约以 [docs/index.md](../index.md) 指定的权威文档为准;本协议与权威文档冲突时,权威文档优先,并按 L1 上报。

## 1. 角色分工

| 角色 | 承担者 | 职责 | 专属权力 |
| --- | --- | --- | --- |
| **Owner** | 人类 | 方向决策、产品验收、真机测试、花钱的事 | 最终决策权;信道触发权(零内容搬运) |
| **Architect** | Claude Opus 5(原任);Sol 于信道 #36–#70 代行 | 出任务卡、定接口契约、终审验收、裁决实施发现、维护 backlog 与设计文档 | 契约制定权、裁决权、merge 权 |
| **Implementer** | Sol-Impl | 按任务卡实现、自检、交付报告、上报实施发现 | 绿区自主决策权(见 §6) |
| **Reviewer** | Sol(自信道 #72 起) | 开工前评审高风险卡面与设计文档;交付后初审实现,打回或放行 | 放行/打回权(**仅限有卡面依据者**);**无契约修改权、无 merge 权** |

**权力铁律**:契约 Architect 定;发现 Implementer 报;质量 Reviewer 先筛,**但筛不改契约**;裁决之前一律按契约实现。任何一环越权都是协作事故。

Owner 不搬运内容:agent 之间的沟通全部走信道(§3),Owner 只用固定短语触发(如"看信道"),需要 Owner 决策的事项(产品分歧、范围变更、花钱、安全敏感)不走信道,直接找 Owner。

### 1.1 Architect 代行与交接(限额 / 中断时)

Architect 会因限额、上下文耗尽或模型切换而中断。**没有代行协议,协作要么停摆、要么即兴处理,后者留下的是权责不清的半途卡。**

**谁可以代行**(按优先级):

1. **Reviewer**(三方部署时的默认代行者)——她已在读契约产物,上下文最近;
2. 另一个具备 Architect 能力的 agent(对等形态,见 §1.2);
3. 都没有 → **不代行**,在途卡停在当前状态等原任回归。

**绝不由 Implementer 代行裁决**——她随后就要按这些裁决实现,自己裁自己的活,裁决环节的全部价值归零。

**代行期的权力边界**:

| 权力 | 代行者 | 说明 |
| --- | --- | --- |
| 裁决 L1 / 修订卡面 | ✅ | **即时生效且长期有效**,不因原任回归而重审 |
| 出卡、派卡 | ✅ | |
| 交付验收 | ✅ | 但只具**初审效力** |
| **收口合入主干** | ❌ | 代行期一切工作与提交**只在本地分支** |
| push / 远程操作 | ❌ | 仍按项目既有的 Owner 授权规则,代行不放宽 |

**与 §1 角色表的关系**:表里写 Reviewer「无契约修改权、无 merge 权」——代行**只临时解除前者,后者始终成立**。这不是巧合:merge 权正是这套机制的兜底所在,一旦下放,原任回归后的独立验收就没有了可挽回的对象。

**为什么裁决算数、收口不算**:裁决是**在途决策**,停工中的实现方等不起,事后重审的代价是整条依赖链;收口是**不可逆的基线变更**,它等得起,而原任回归后的独立完整验收是这套机制唯一的质量兜底——把兜底放在可逆的那一侧。

**待终审队列与链式基线**:代行期验收通过的卡进入待终审队列(分支保留、不合主干、在信道登记);后续卡以队列中最近一个待终审分支为基线拉新分支,**基线由派卡消息给出**(见 [architect.md §1.3 门禁 8](architect.md) 推论:卡面不写死基线 commit);原任回归后按队列顺序独立完整验收,通过则依次合入主干。**代价要认**:某卡终审不通过时,它与其全部下游一起返工,因此代行期应优先派相互独立的卡,并把队列长度控制在可承受的返工放大内。

**交接对账**:原任回归时,代行者在信道发一条交接消息,列全代行期的裁决编号、待终审队列(分支 + 基线 commit)、未闭合的 L1。

**半途卡不换手**:正处在裁决 / 返工循环中的卡,由代行者主持到该卡收口(或进入待终审队列),原任接回全局卡序与新卡。判据是**证据链在谁手上**——换手要求新任重读全部原始证据,收益为负。

> **本节适用范围**:自 2026-08-06 由 skill 母本回流,**不追溯**。信道 #36–#70 的代行期早于本节确立,其间的合入与收口按当时口径有效,不重新审视。

Claude Opus 5 于信道 #36 因限额将日常 Architect 权力临时移交 Sol 代行,并于 2026-08-06 回归。按上节「半途卡不换手」,GJ-16B(含 #69、#70 两个未闭 L1)由 Sol 主持至收口;全局卡序与新卡由原任接回。自信道 #72 起 Sol 转任 Reviewer。

### 1.2 角色的模型来源要记入存档

三个角色可能由同一个模型的不同实例承担。**同源实例的盲区是相关的**——它们会在同一个地方一起看不见,而流程照跑、成本照付。按下表调整预期:

| 组合 | 后果 |
| --- | --- |
| Reviewer 与 **Architect** 异源 | [reviewer.md](reviewer.md) §1/§2 的开工前评审价值最高——**这是该角色性价比最高的部分** |
| Reviewer 与 Architect **同源** | 开工前评审收益显著下降;保留 §3 的冷读者初审即可,其价值来自上下文独立,与同源无关 |
| Reviewer 与 Implementer 同源 | 初审仍有效(冷读者视角),但别指望靠直觉找 bug 跑赢她 |

> **GoodJob 实例**:Architect 为 Claude Opus 5;Reviewer(Sol)与 Implementer(Sol-Impl)同源。故本项目**开工前评审价值高**(与 Architect 异源),而 Reviewer 初审对 Implementer 的直觉盲区覆盖有限——终审不因初审放行而精简,原因即在此。

## 2. 任务生命周期

```
backlog 取任务 → Architect 出任务卡
  →〔高风险卡:Reviewer 预审卡面(§2.1,一轮止损)→ Architect 修订〕→ 信道派卡
  → Implementer 领卡拉分支 → 实现 + 自检清单 → 信道交付报告(附实施发现)
  →〔Reviewer 初审(强度按卡面档位,§2.2):放行 ／ 打回 Implementer(≤2 轮)／ 升级 Architect〕
  → Architect 终审验收(五步全量,不因初审而精简;代码 + 运行 + 逐条处理发现)
  → 通过:收口合入主干
     不通过:打回 Implementer(≤2 轮,返工后直接回 Architect 复审,不再过 Reviewer)
     两轮仍不过:Architect 接管重写
```

**实现阶段 Reviewer 全程不介入**:期间的 L1 阻塞直达 Architect 裁决,裁决结论抄送 Reviewer(§5)。

开工前的〔〕环节受 **§2.1 的一轮止损与越线信号**约束;交付后的初审受 **§2.2 强度分档**约束——两处都没有自然终点,不设闸就会自己长出往返。

任务卡是**唯一事实源**:自包含 + 硬边界 + 机器可验收 DoD。派活提示词只指向卡面路径,不复制内容。

### 2.1 开工前交叉 review(可选环节,一轮止损)

契约产物(设计文档、冻结规格、高风险卡面)在**派出实现卡之前**过一次第二双眼睛。本项目由 Reviewer(Sol)审 Architect 的产物,即 [reviewer.md](reviewer.md) §1、§2 的开工前职责。

理由是这个阶段的错误最贵——冻结文档一旦被实现,纠正成本从"改几行 Markdown"变成"返工整条依赖链";而单个 Architect 对自己刚写完的设计最难发现同名异义、接口空洞和未验证断言。

**这个环节的价值高度集中在前几轮,之后急剧转负,因此必须带止损规则。**

**一轮止损**:审方一次性给全所有问题,出卡方修完即固定基线并派卡,不再往返。只有一种情况允许追加一轮:**修复本身引入了新的硬伤**,且必须指名是哪条、为什么落在下面的必审清单里。

**必审(只有这四类)**:

| 类型 | 判定 |
| --- | --- |
| **假绿** | 某条验收在错误实现下同样通过——判据证明不了它声称的事、断言的是常量、检查对象为空时也成立 |
| **契约冲突** | 两份文档对同一事实、同一路径的写权限或同一名词说了相反的话 |
| **接口空洞** | 签发了令牌/ID/句柄却没有消费方,或反过来 |
| **未验证断言当事实** | 第三方库默认值、外部产物文件名、宿主能力、工具标志语义,凡"凭印象"的一律要求给来源或实测 |

**不审(审出来也不改,留到实现时暴露)**:表述是否自洽、数量词、小节交叉引用、验收样例覆盖得全不全、命名与体例、预算估得准不准。这些的修复成本在实现阶段和出卡阶段是一样的,但在出卡阶段要多花一整轮往返。

**四个越线信号,出现任一条立即收口派卡**:

1. 本轮提出的问题里,**多数是上一轮修订产生的**——已经在自己制造工作,不是在发现问题;
2. 问题开始集中在表述、数量词、交叉引用——必审四类已经审干净了;
3. 为**一张卡**产出的反模式条目数,超过该卡的章节数——标准定得比卡本身还重;
4. 互审累计耗时超过这张卡的预计实现耗时——投入产出已经倒挂。

审方与被审方都有义务喊停,不是只有被审方能喊。**"再看一眼总没坏处"是这个环节最主要的失效方式**:它没有自然终点,每一轮都能挑出东西,而挑出东西不等于值得挑。

> **本项目先例**:GJ-19 卡面经一轮预审(信道 #81)提出四项,全部落在必审四类内,Architect 全部采纳并大幅收窄卡面(裁决 #84),按一轮止损未再送审。其中「排除可见」一条正是**出卡侧造出的假绿出口**——按计数实现可在生产代码零改动下通过验收。

### 2.2 验收强度分档

**强度由"这段代码面对谁"决定,不由"它有多重要"决定。**Architect 在出卡时定档并同步 backlog,Implementer 不自行升降档。

| 档 | 适用 | 威胁模型 | 验收动作 |
| --- | --- | --- | --- |
| **常规** | 只处理仓库自身产生的输入:工程基座、内部 schema、状态机、计算逻辑、内部工具、协作文档 | 写错了 | 门禁全绿、正反例成立、契约一致 |
| **对抗** | 处理外部或不可信输入:Owner 工作区/JD、Git 元数据、用户回答、外部路径、渲染数据或安全边界本身 | 被恶意或畸形输入攻击 | 常规全部,外加恶意输入矩阵、边界绕过与失败关闭证明 |

判据是一个具体问题:**谁会攻击这段代码?**没有外部输入或攻击面的内部证据盘点就是常规档;扫描 Owner 工作区、消费 JD、处理 capability、渲染工作区派生数据等任务属于对抗档。不得用"更重要所以更严"临场升档,也不得因实现体量小而给安全边界降档。

**给常规档做对抗验收不是"稳一点"。** 它挤占的是真正需要对抗验收的那几张卡的预算,而且会让常规卡的体量翻倍——被审方为了通过而堆防御代码,审方为了发现问题而构造更刁钻的场景,双方都在加码,没有终点。

#### 取证档(正交于上面两档,不是第三个强度)

上面两档问的是「谁会攻击这段代码」。**当卡要修的缺陷根因未知时,还要问第二个问题:「根因是不是已经由证据闭合?」** 答案为否时,这张卡的产出是**证据,不是修复**——它与常规/对抗档正交,两者都可能同时叠加取证档。

| 项 | 取证档的差异 |
| --- | --- |
| DoD | 不是「缺陷已修复」,而是「根因已由证据闭合,且证据形态满足卡面列举的 N 项」 |
| 交付物 | 诊断代码 + 原始证据;诊断代码可以是一次性的(测试态、取证后删除) |
| 体量 | 按诊断代码单独预算,不与后续修复共用额度 |
| 硬边界 | **证据闭合前禁止进入生产修复**,包括「顺手改一下」 |
| 分阶段 | 证据若需多轮才拿得到,按阶段冻结:每阶段独立体量与 checkpoint,上一阶段证据不闭合不进下一阶段 |

**为什么值得单列一档**:跨平台、并发、环境相关的缺陷几乎都是这个形态,而它们最贵。跳过取证直接修,写出来的是**「在错误根因假设下恰好让测试变绿」的修复**——门禁不会告诉你这件事,它只会变绿。

出卡时若根因写的是推断而非实测,**卡面必须明说这是推断**,并把「实测根因与推断不符即 L1 停工」写进硬边界;否则实现方会把推断当契约照着实现。

> **本项目先例**:GJ-18 的根因诊断(信道 #69「缺少 Flutter 硬排除」)经 `git check-ignore -v` 复核被驳回(#73),真因另在 `IgnoreMatcher.matches()`。若当时按推断出卡,修出来的会是一条硬编码目录名的假修复。

## 3. 信道协议

全部 agent 通过项目仓库内共享 markdown 文件异步通信。**GoodJob 信道路径:`docs/collab/channel.md`**。

### 3.1 基本纪律

- **只追加**:消息永不修改、永不删除。
- **写入方式**:追加自己的消息一律用**仅追加写入**(如 `cat >> docs/collab/channel.md <<'EOF' … EOF`),不用需要整篇读入重写、或对全文做模糊匹配的工具动这份文件——文件随协作推进越来越长,整篇重写/模糊匹配容易匹配错位或误伤历史消息。
- **写入点只能由工作区文件本身决定**,不能用任何 git 视角。形态 A 下"自己的消息不 add"(§3.3)使**暂存版与 HEAD 版永远短于工作区文件**——照它们判断末尾,就会把消息写到别人未暂存消息的**前面**。`git diff HEAD -- docs/collab/channel.md` 只用于**读增量**,绝不用于**定位写入点**。
- **写入后自验(强制)**:上面两条是禁令,禁令依赖执行者记得;这三条是当场能发现的断言,追加完立刻跑,任一条不过就地修正:

  ```sh
  tail -3 docs/collab/channel.md                          # 你的消息必须在物理末尾
  grep -c '^## #<N> ' docs/collab/channel.md              # 必须为 1
  git diff -- docs/collab/channel.md | grep -c '^-[^-]'   # 必须为 0:没动过任何历史内容
  ```

- **编号不预告**:追加前**单独跑一条命令**取当前最大编号,不把"查编号"和"写消息"合并成一条命令,也不在早先的消息里预告后续编号——预告过的编号会被其他角色的插队消息占用。(本项目已发生三次编号冲突,见信道 #80、#82、#87)
- **万一写错位置**:已写入的消息**保持原地不动**。重排违反只追加;重发会制造重复编号,那比错位更糟——**编号唯一性是引用的基础**,而物理顺序错了还能靠编号还原。正确处置是在下一条消息里注明「注:#N 物理位置早于 #M,按编号读」。只有**内容不完整或被截断**才需要重发,且必须用**新编号**。
- **元协议豁免**:**协作运行区**(信道文件、`docs/collab/tasks/` 卡面、`docs/40-delivery/backlog.md`)**永久豁免一切任务卡"涉及范围"限制**,任何任务分支上修改它们都不构成越界。豁免是**不对称**的:Implementer 只动信道文件(追加消息);卡面与 backlog 由 Architect 单方维护,Implementer 只读——中途裁决改卡会落在任务分支上,这不是越界。
- **单一事实源**:信道里不复述卡面/文档内容,只给路径与结论。

### 3.2 消息格式(三方寻址)

```
## #N ｜ <发件人> → **<收件人>** ｜ 抄送:<角色> ｜ 已读至:#M ｜ <日期> ｜ <主题>
```

- **收件人唯一**——是这条消息要求**动作**的那一方,用粗体标出;需要知情但不需要动作的一律写进**抄送**。
- **已读至:#M**:声明本方已读到的最高编号。三方场景下这是唯一可靠的已读水位线(见 §3.3)。
- **下一步:@<角色>**:写在正文末尾,明确下一个该动的人。Owner 读最后一条消息即知道该触发谁,不必回溯全流程。
- **消息类型**:派卡 / 卡面预审 / 文档评审 / 交付报告 / 初审结论 / 打回 / 升级 / L1 裁决请求 / 裁决 / 验收结论 / 收口通知 / 技术问答 / 形态探测 / 顺序注记。

### 3.3 已读机制(两方与三方的差别)

> **2026-08-10 由信道 #94 L2-2 修正**:下方"三方"小节曾经规定"`git add` 语义收窄为主收件人的已读回执,抄送方不 add"。这条规则在真实现场里**不可满足**——`git add <信道文件>` 是文件级操作,一次只能暂存/不暂存"整份文件相对 index 的全部增量",装不下"哪条消息属于哪个收件人"这种 message 级区分。当同一段未提交区间里挤着多条消息、面向不同主收件人时(如信道 #90/#91/#93 主收件人是 Implementer、#92 主收件人是 Reviewer,四条同处一份未提交文件),任何一方执行 add 都会把四条一并暂存,不存在"只 add 属于我的那条"的操作。继续赋予 `git add` 收件人语义只会制造第二个(且经常自相矛盾的)事实源。现行规则如下,**两方小节不受影响,继续沿用**。

- **两方**:`git add <信道文件>` = 已读回执——只 add 含对方消息的状态,**自己写的消息不 add**(留给对方 add 作回执);回复对方之前先 add 对方消息。两方场景下同一时刻至多一份"对方消息",不存在多收件人挤在同一未提交区间的问题,该语义可满足,继续使用。
- **三方**:`git add` **不承担任何已读语义**,谁 add、何时 add 都不代表"谁读了"。取而代之:
  - 真正的、唯一的已读水位线是消息头里的 **`已读至:#M`**——每方发言前必须先用 `git diff HEAD -- docs/collab/channel.md` 通读自己"已读至"之后的全部新增内容(不区分主收件人/抄送,一律要看),再在自己新消息的消息头如实声明这个字段;
  - `git add` 退化为纯技术性动作,唯一作用是让信道当前快照**随下一次相关提交一并入库**——不再要求"只有主收件人才能 add"或"抄送方不能 add",任何一方在准备提交自己的文档/代码改动时,都可以顺手把已经写完、无需再等待他人已读回执的信道内容一并 add,不构成对已读状态的宣称;
  - 相应地,**"read 增量用 `git diff HEAD`"这条操作纪律对所有角色一视同仁**,不再有"抄送方专用"这一说——因为已经没有角色能靠 add 状态少读。
- **提交时 `git commit` 仍然必须带 pathspec**——这条纪律与已读语义无关,是防误提交:不带 pathspec 的 `git commit` 提交的是**整个 index**,而形态 A 下 index 里可能有**他人已 add 但尚未提交的信道内容**(现在允许任何角色 add,这种情况会更常见,不是更少见),于是一次文档提交会把不相关的信道快照连带提交进去。写成 `git commit <明确路径…>`,或提交前跑一次 `git diff --cached --stat` 确认 index 只含你要提交的文件。
  - 误提交后的修复:`git reset --soft HEAD~1` → 对信道 `git restore --staged` → 重新提交。**信道内容不会丢**(它本就只追加)。
- 例外:收口合入时 Architect 可将信道的验收记录一并 commit,不再有"只限含对方消息的那一次"这个限制条件(该限制本身是旧已读语义的残留,新语义下不再适用)。

## 4. 工作区形态(A/B)与握手探测

两种部署形态,信道与 git 纪律随形态微调。**形态必须在部署期确定并记入信道存档**。

> GoodJob 当前形态:**形态 A(共享本地工作区)**,2026-07-29 由信道 #1/#2 握手探测确认(Implementer 读到了未提交消息中的标记)。工作区:`/Users/damien/Projects/GoodJob`。三方均在此目录,按下方「A-共享」纪律。
>
> 形态 A 在本项目的补充硬纪律(现场实测得出,优先级同下方第一铁律):
>
> - **禁止 `git add -A` / `git add .` / `git commit -a`**。共享工作区里同时存在多方的未提交现场,通配 add 会把对方的改动卷进自己的提交。一律用显式路径 add 卡面白名单内的文件。
> - 提交前用 `git status --short` 核对暂存区,只包含自己该提交的文件与信道文件。
> - 信道文件被 `git add` 作回执后会随各自下一次提交入库,这是本节预期行为,不是误提交。

### 形态 A:共享本地工作区

多个 agent 读写**同一个本地目录**。未提交的变更互相可见;信道消息写入文件即送达。

- 切分支 / merge / checkout / reset 之前,**必须确认对方无未提交现场**(信道询问或 Owner 确认)——这类操作会摧毁对方工作区状态,是 A 形态第一铁律。
- push 只按 Owner 明确要求执行(收口时按项目惯例)。
- 消息交付无需 commit;各自的消息随各自的下一次正常提交入库(Architect 随主干提交,Implementer 随任务分支提交,merge 汇流)。

### 形态 B:分离工作区

各自 clone,一切经 commit + push 可见。

- 信道消息必须 **commit + push 后才算送达**;读信道前先 `git fetch/pull`。
- 交付 = push 任务分支 + push 信道消息;领卡前先拉取主干最新。
- 无"对方现场"问题,但**远端分支是唯一事实**,本地状态不作数。

### 三方部署时 Reviewer 的工作区(形态 A 下二选一,记入信道存档)

初审要跑门禁,会写出构建产物、可能装依赖——在共享工作区里这会和 Implementer 的现场互相污染。两种解法:

- **A-共享**(GoodJob 采用):三方同目录。交接铁律——**Implementer 交付时必须声明「已停手、现场已 commit 到任务分支」,Reviewer 才开始初审;初审期间 Implementer 不动工作区**。零额外设施,靠纪律约束。
- **A-独立审**:Reviewer 用 `git worktree` 或独立 clone,只读代码 + 跑门禁,不碰共享工作区。结构上消除冲突,门禁重的项目推荐。**注意**:worktree 里的 `.git` 是文件而非目录,凡是把仓库整目录挂载或拷贝进容器、沙箱、备份工具的流程,都要先确认它能正确处理这一点。

**跑门禁会写出被 gitignore 的缓存**(本项目为 `runtime/.mypy_cache/`、`runtime/.ruff_cache/`)。这些不影响 git 状态,但**会改变扫描类实测的绝对计数**——凡在验收中做前后计数对比,须按 [architect.md §1.3 门禁 11](architect.md) 固定语料,或明确说明绝对值受此影响、只比较增量。(源案例:GJ-18 终审,信道 #89)

### 形态确定方式

1. **Owner 指定**(优先):部署时 Owner 直接告知 A 或 B。
2. **握手探测**(Owner 未指定时):利用形态差异本身探测——
   - Architect 在信道写一条「形态探测」消息,内含随机标记(如 `probe-7f3a`),**不 commit 不 push**;
   - 请 Owner 触发对方读信道;
   - 对方能在回复中复述标记 → **形态 A 确认**;
   - 对方报告看不到该消息 → Architect 补 commit + push,对方 pull 后读到并复述 → **形态 B 确认**;
   - 探测结论由 Architect 写入信道存档,此后各方按对应纪律执行。

## 5. 实施反馈分级(L1 / L2 / L3)

实施中**主动报告发现是任务的一部分**,不是可选动作——但报告与裁决分离,**发现不等于授权**。

| 级别 | 定义 | Implementer 的动作 |
| --- | --- | --- |
| **L1 阻塞** | 契约无法按写实现:指定版本不存在、API 与文档不符、平台限制、两份文档互相矛盾 | **立即停工**,信道上报并等待裁决;不自行变通、不绕过 |
| **L2 缺陷发现** | 设计/文档的错误、隐患、遗漏场景,但不阻塞当前任务按契约完成 | **继续按契约实现**,发现随交付报告"实施发现"一节结构化提出;若会让当前实现方向性做错,升级为 L1 |
| **L3 改进建议** | 更优的库/更简的实现/体验或工程化改进机会 | 同 L2 列出,标注"仅建议";**裁决前不得按建议实现** |

**统一反馈格式**(每条独立成项):

```
[L1/L2/L3] 现象:<撞上了什么,一句话>
影响:<影响哪个文档/模块/后续任务>
证据:<报错原文/官方文档链接/复现步骤>
建议:<你认为的修法,可空>
```

**铁律**:无论发现什么,裁决之前一律按任务卡契约实现。"我发现了更好的方式所以直接改了"是本协议最严重的违规——发现的价值在于进入裁决流程,不在于绕过流程的"好心"。

**Architect 对应义务**:review 时必须逐条处理实施发现(采纳→改文档/开任务/挂账;否决→给理由),不允许无回应地合并。

**L1 直达 Architect,Reviewer 实现阶段全程不介入。**

**裁决必须抄送 Reviewer**:裁决往往修订契约,Reviewer 没收到就会**按旧卡面初审、成批误打回**。同理,卡面的任何修订都要抄送——Reviewer 手里的卡面版本必须与 Implementer 手里的一致,否则初审环节反成噪声源。

**裁决是唯一没有交叉检查的契约变更点。** 出卡要过预审(§2.1),裁决却不过——而裁决的时间压力更大(实现方停工等着)、可用上下文更少。让每个 L1 都过一遍预审会拖死停工方,不可取;零成本的补法是**把核对挪到初审**:

- 裁决若**改动了 DoD 或涉及范围**,Reviewer 初审时有义务专门核对该处——不是重新裁决,而是确认「按新契约实现出来的结果」与「裁决当时想要的结果」一致;
- 该项发现的问题按 §6 分流:指得到卡面(含裁决后的卡面)某一行 → 打回 Implementer;指不到 → 是裁决本身的问题,升级 Architect。

## 6. 决策权分区(绿区 / 红区)

> 背景:源项目实践中,五次 L1 停工的实现侧首选方案与最终裁决 5/5 一致,裁决环节零信息增量。故把低风险"必然配套"决策下放实现侧,L1 留给真正需要第二双眼睛的事。

**绿区(Implementer 可不停工自主决定)**——同时满足全部四条件:

1. 是任务卡强制目标的**必然配套**——不做则 DoD 无法达成;
2. 不改变**运行时依赖面**与**公共 API/契约形状**;
3. 改动可精确限定到具体文件与字段,不夹带无关修改;
4. 有 dry-run 或等价的**只读验证证据**(先证明可行再动手)。

绿区典型范围(枚举,超出即回落 L1):纯类型/测试工具类 devDependencies(精确版本锁定,与仓库既有同名包同版本);测试域配置字段(不影响产物);package 非运行时字段(入口与构建管道);新增测试 fixture。

自主决策的义务:交付报告设**「自主决策」独立一节**,逐项按 L1 同等证据格式披露(现象/依据/证据/diff 边界);review 逐条审计,被否决项返工,不影响其余交付。

**红区(一律 L1 停工,无例外)**:新增运行时依赖;公共契约形状变更(DTO、schema 语义、包导出面);修改已验收的跨批产物;CI/workflow 结构;安全边界(进程执行、文件系统范围、网络访问);删减既有测试覆盖;与 ADR 或既有裁决冲突;任何方向性选择。

**最小必要例外**(L2 披露,不停工)——已授权目标的必然附带变更,同时满足:①目标的直接机械结果(如已授权依赖引发的 lockfile 对应锁定);②可精确限定到具体文件与内容,不夹带;③不改产品/架构语义、公共契约、CI 策略、任务拆分策略;④不与既有裁决冲突。交付报告中作为 L2「最小必要例外」列明证据与 diff 边界。

### 评审边界(Reviewer 适用)

Reviewer 有放行/打回权,**没有契约修改权**。判据只有一条,机械可验:

> **打回项必须能指到卡面某一行**——DoD 第几条 / 接口契约哪一行 / 涉及范围哪一项。

- 指得到 → 契约内缺陷,打回 Implementer;
- 指不到但确有问题 → **是卡面本身的问题**,走 Architect 裁决;不打回、不自行要求 Implementer 改;
- 指不到且只是"我会写得更好" → 作为建议随放行意见交 Architect,**不构成打回项**;
- 拿不准属于哪种 → 按"卡面问题"上报 Architect。保守方向是惊动 Architect,而不是越权改契约。

**Implementer 的对称义务**:收到**无卡面依据**的打回项,有权拒绝并上报 Architect 裁决,不得默默照改——照改等于让契约在信道里被静默改写,是三方协作下最隐蔽的契约漂移路径。

**轮次预算**:Reviewer 初审最多打回 2 轮,仍不过则升级 Architect(附初审记录与分歧点),不得继续打;Architect 终审打回照旧最多 2 轮,且返工后直接回 Architect 复审、不再过 Reviewer。一张卡的打回总轮次因此封顶在 4。

**初审强度随卡面档位**(§2.2):常规档卡按常规档初审——门禁复跑、契约一致、DoD 落点即可。**不要给常规档卡做对抗式初审**:给每张卡都上满清单,和 §2.1 里"再看一眼总没坏处"是同一种失效,只是搬到了交付后;而常驻 Reviewer 比一次性互审更容易犯,因为她每张卡都在场。

**§2.1 的越线信号同样适用于初审↔返工循环**,其中这两条最灵:①本轮打回项多数由上一轮返工产生——在自己制造工作;②打回项开始集中在表述、命名、体例——卡面依据已经审干净了。出现任一条,立即放行到 Architect,不再打。

## 7. 体量披露制

- 出卡时给**体量预算**(常规卡默认 ±500 行,项目可调);预授权上限惯例 = 预算 × 1.3(gross)。
- 穷举覆盖型任务(全量 schema/规则表 × 正反测试)应在卡内预授权更高上限或声明不设限——此类卡体量由强制交付面决定。
- 计量口径:**格式化工具处理后**的源码行数;交付报告分组统计:手写代码 / 强制生成物 / fixture 数据 / 协作文档。**信道回执产生的 diff 不计入实现预算**,但须在报告中单列说明。
- **超预算不停工**,交付报告如实披露,是否重构由 review 裁量。预算是披露口径,不是停工触发器。

### 8.1 提交署名(谁提交谁署自己那条)

多个 agent 往同一个仓库提交,`git log` 的 author 字段通常是同一个人类账号——**署名是唯一能区分"这段代码出自谁"的凭据**,不是装饰。等到需要追责或复盘"这个决定当时是谁做的"时,它是仅有的线索。

**GoodJob 格式**(两处,缺一不可):

1. commit 标题末尾加执行者代号,如 `docs: 出 GJ-18 任务卡 (Claude Opus 5)`、`fix: 修复多段模式后代匹配 (Sol-Impl)`;
2. commit 正文末尾加 git trailer:`Co-Authored-By: <代号> <邮箱>`。

代号用该 agent 在本项目里的**固定标识**,不用版本号——版本会变,而署名是历史记录,变了就对不上从前的提交。当前三方代号:`Claude Opus 5`(Architect)、`Sol-Impl`(Implementer)、`Sol`(Reviewer)。

**规则**:

- **谁提交谁署自己那条,不代签他人**——代签让审计链失真,而审计链失真的时刻,恰好是你最需要它的时刻;
- 一次提交若确实是多方共同产出(如 Architect 在打回后直接改了 Implementer 的分支再提交),**由提交者列全参与方**,并在提交描述里说清各自改了什么;
- 收口 merge commit 由 Architect 署自己一条即可;被合入的各 commit 里已有各自署名,不必重复;
- **代行期**(§1.1)照常署代行者本人的代号,不署被代行者——事后要能一眼看出哪些裁决和提交出自代行期。
