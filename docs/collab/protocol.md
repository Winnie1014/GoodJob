# 共同协议(Common Protocol)

> 本文件是双 agent 协作的共同底座,Architect 与 Implementer 都必须完整遵守。
> 角色专属操作手册:[architect.md](architect.md) / [implementer.md](implementer.md)。
> 历史教训:[anti-patterns.md](anti-patterns.md)。本协议源自 CodeRoute 项目协作规范 v1.5 及其实践演化。
>
> **GoodJob 实例说明**:本文件是协作运行区文档,不是产品契约。产品与架构契约以 [docs/index.md](../index.md) 指定的权威文档为准;本协议与权威文档冲突时,权威文档优先,并按 L1 上报。

## 1. 角色三角

| 角色 | 承担者 | 职责 | 专属权力 |
| --- | --- | --- | --- |
| **Owner** | 人类 | 方向决策、产品验收、真机测试、花钱的事 | 最终决策权;信道触发权(零内容搬运) |
| **Architect** | agent 甲 | 出任务卡、定接口契约、review、裁决实施发现、维护 backlog 与设计文档 | 契约制定权、裁决权、merge 权 |
| **Implementer** | agent 乙 | 按任务卡实现、自检、交付报告、上报实施发现 | 绿区自主决策权(见 §6) |

**权力铁三角**:契约 Architect 定;发现 Implementer 报;**裁决之前一律按契约实现**。任何一环越权都是协作事故。

Owner 不搬运内容:两个 agent 之间的沟通全部走信道(§3),Owner 只用固定短语触发(如"看信道"),需要 Owner 决策的事项(产品分歧、范围变更、花钱、安全敏感)不走信道,直接找 Owner。

## 2. 任务生命周期

```
backlog 取任务 → Architect 出任务卡 → 信道派卡 → Implementer 领卡拉分支
→ 实现 + 自检清单 → 信道交付报告(附实施发现) → Architect 验收(代码 + 运行 + 逐条处理发现)
→ 通过:收口合入主干;不通过:批注打回(最多两轮,仍不过则 Architect 接管重写)
```

任务卡是**唯一事实源**:自包含 + 硬边界 + 机器可验收 DoD。派活提示词只指向卡面路径,不复制内容。

## 3. 信道协议

双 agent 通过项目仓库内共享 markdown 文件异步通信。**GoodJob 信道路径:`docs/collab/channel.md`**。

- **只追加**:消息永不修改、永不删除;用 `git diff` 读增量。
- **编号**:消息编号 `#N` 全局严格递增,回复引用编号(如"就 #12 的 L1")。
- **消息头格式**:`## #N ｜ <发件人> → <收件人> ｜ <日期> ｜ <主题>`
- **消息类型**:派卡 / 交付报告 / L1 裁决请求 / 裁决 / 验收结论 / 收口通知 / 技术问答 / 形态探测。
- **已读机制**:`git add <信道文件>` = 已读回执——**只 add 含对方消息的状态,自己写的消息不 add**(留给对方 add 作回执);回复对方之前先 add 对方消息。例外:收口合入时 Architect 可将信道记录一并 commit。
- **元协议豁免**:信道文件**永久豁免一切任务卡"涉及范围"限制**——任何任务分支都可以且应该修改它来追加消息,不构成越界。
- **单一事实源**:信道里不复述卡面/文档内容,只给路径与结论。

## 4. 工作区形态(A/B)与握手探测

两种部署形态,信道与 git 纪律随形态微调。**形态必须在部署期确定并记入信道存档**。

> GoodJob 当前形态:**形态 A(共享本地工作区)**,2026-07-29 由信道 #1/#2 握手探测确认(Implementer 读到了未提交消息中的标记)。工作区:`/Users/damien/Projects/GoodJob`。
>
> 形态 A 在本项目的补充硬纪律(现场实测得出,优先级同下方第一铁律):
>
> - **禁止 `git add -A` / `git add .` / `git commit -a`**。共享工作区里同时存在双方的未提交现场,通配 add 会把对方的改动卷进自己的提交。一律用显式路径 add 卡面白名单内的文件。
> - 提交前用 `git status --short` 核对暂存区,只包含自己该提交的文件与信道文件。
> - 信道文件被 `git add` 作回执后会随各自下一次提交入库,这是本节预期行为,不是误提交。

### 形态 A:共享本地工作区

两个 agent 读写**同一个本地目录**。未提交的变更互相可见;信道消息写入文件即送达。

- 切分支 / merge / checkout / reset 之前,**必须确认对方无未提交现场**(信道询问或 Owner 确认)——这类操作会摧毁对方工作区状态,是 A 形态第一铁律。
- push 只按 Owner 明确要求执行(收口时按项目惯例)。
- 消息交付无需 commit;各自的消息随各自的下一次正常提交入库(Architect 随主干提交,Implementer 随任务分支提交,merge 汇流)。

### 形态 B:分离工作区

各自 clone,一切经 commit + push 可见。

- 信道消息必须 **commit + push 后才算送达**;读信道前先 `git fetch/pull`。
- 交付 = push 任务分支 + push 信道消息;领卡前先拉取主干最新。
- 无"对方现场"问题,但**远端分支是唯一事实**,本地状态不作数。

### 形态确定方式

1. **Owner 指定**(优先):部署时 Owner 直接告知 A 或 B。
2. **握手探测**(Owner 未指定时):利用形态差异本身探测——
   - Architect 在信道写一条「形态探测」消息,内含随机标记(如 `probe-7f3a`),**不 commit 不 push**;
   - 请 Owner 触发对方读信道;
   - 对方能在回复中复述标记 → **形态 A 确认**;
   - 对方报告看不到该消息 → Architect 补 commit + push,对方 pull 后读到并复述 → **形态 B 确认**(补推过程本身就完成了 B 形态的通路验证);
   - 探测结论由 Architect 写入信道存档,此后双方按对应纪律执行。

## 5. 实施反馈分级(L1 / L2 / L3)

实施中**主动报告发现是任务的一部分**,不是可选动作——但报告与裁决分离,**发现不等于授权**。

| 级别 | 定义 | Implementer 的动作 |
| --- | --- | --- |
| **L1 阻塞** | 契约无法按写实现:指定版本不存在、API 与文档不符、平台限制、两份文档互相矛盾 | **立即停工**,信道上报并等待裁决;不自行变通、不绕过 |
| **L2 缺陷发现** | 设计/文档的错误、隐患、遗漏场景,但不阻塞当前任务按契约完成 | **继续按契约实现**,发现随交付报告"实施发现"一节结构化提出;若会让当前实现方向性做错,升级为 L1 |
| **L3 改进建议** | 更优的库/更简的实现/体验或工程化改进机会 | 同 L2 列出,标注"仅建议";**裁决前不得按建议实现** |

**统一反馈格式**(每条独立成项):

```
[L1/L2/L3] 现象:<撞上了什么,一句话>
影响:<影响哪个文档/模块/后续任务>
证据:<报错原文/官方文档链接/复现步骤>
建议:<你认为的修法,可空>
```

**铁律**:无论发现什么,裁决之前一律按任务卡契约实现。"我发现了更好的方式所以直接改了"是本协议最严重的违规——发现的价值在于进入裁决流程,不在于绕过流程的"好心"。

**Architect 对应义务**:review 时必须逐条处理实施发现(采纳→改文档/开任务/挂账;否决→给理由),不允许无回应地合并。

## 6. 决策权分区(绿区 / 红区)

> 背景:源项目实践中,五次 L1 停工的实现侧首选方案与最终裁决 5/5 一致,裁决环节零信息增量。故把低风险"必然配套"决策下放实现侧,L1 留给真正需要第二双眼睛的事。

**绿区(Implementer 可不停工自主决定)**——同时满足全部四条件:

1. 是任务卡强制目标的**必然配套**——不做则 DoD 无法达成;
2. 不改变**运行时依赖面**与**公共 API/契约形状**;
3. 改动可精确限定到具体文件与字段,不夹带无关修改;
4. 有 dry-run 或等价的**只读验证证据**(先证明可行再动手)。

绿区典型范围(枚举,超出即回落 L1):纯类型/测试工具类 devDependencies(精确版本锁定,与仓库既有同名包同版本);测试域配置字段(不影响产物);package 非运行时字段(入口与构建管道);新增测试 fixture。

自主决策的义务:交付报告设**「自主决策」独立一节**,逐项按 L1 同等证据格式披露(现象/依据/证据/diff 边界);review 逐条审计,被否决项返工,不影响其余交付。

**红区(一律 L1 停工,无例外)**:新增运行时依赖;公共契约形状变更(DTO、schema 语义、包导出面);修改已验收的跨批产物;CI/workflow 结构;安全边界(进程执行、文件系统范围、网络访问);删减既有测试覆盖;与 ADR 或既有裁决冲突;任何方向性选择。

**最小必要例外**(L2 披露,不停工)——已授权目标的必然附带变更,同时满足:①目标的直接机械结果(如已授权依赖引发的 lockfile 对应锁定);②可精确限定到具体文件与内容,不夹带;③不改产品/架构语义、公共契约、CI 策略、任务拆分策略;④不与既有裁决冲突。交付报告中作为 L2「最小必要例外」列明证据与 diff 边界。

## 7. 体量披露制

- 出卡时给**体量预算**(常规卡默认 ±500 行,项目可调);预授权上限惯例 = 预算 × 1.3(gross)。
- 穷举覆盖型任务(全量 schema/规则表 × 正反测试)应在卡内预授权更高上限或声明不设限——此类卡体量由强制交付面决定。
- 计量口径:**格式化工具处理后**的源码行数;交付报告分组统计:手写代码 / 强制生成物 / fixture 数据 / 协作文档。
- **超预算不停工**,交付报告如实披露,是否重构由 review 裁量。预算是披露口径,不是停工触发器。

## 8. 通用工程规约(默认值,部署时按项目覆盖)

| 项 | 规约 |
| --- | --- |
| 类型安全 | Python:`mypy` strict,覆盖 `src`/`tests`/`scripts`。TypeScript:`strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`,禁隐式 `any` |
| 错误处理 | 显式错误类型;本地命令边界只返回 `goodjob.errors` 中带稳定 `code` 的错误,不向外泄露栈或路径细节 |
| 注释/文案 | **代码注释、docstring、`ScanIssue` 文案沿用运行时既有的英文**;协作文档、任务卡、信道消息、看板 UI 文案与产品文档用简体中文。注释解释"为什么"而非"是什么" |
| 提交 | Conventional Commits(feat/fix/docs/refactor/test/chore + 中文描述);**commit 描述尾注执行者身份**(如 `(Sol)` / `(Claude Opus 5)`)——双 agent 同仓提交,审计必需 |
| 分支 | `task/<ID>-短描述`;单卡一分支;批量模式:统一分支、按卡独立 commit |
| 依赖 | **运行时 Python 侧 `dependencies = []` 是刻意的供应链边界,任何新增运行时依赖一律红区 L1**。dev 依赖与前端 devDependencies 需卡面明确批准并列 companion 闭包 |
| 平台 | 运行时当前是 macOS-only(`sandbox-exec` + BSD `ps`),见 README 环境要求;涉及路径/进程/文件的代码仍按 `O_NOFOLLOW`、descriptor-relative 的既有写法,不引入新的平台假设 |
| 安全边界 | 进程执行、文件系统范围、网络访问、capability 传递、CSP 与转义规则**全部红区**,一律 L1;`SKILL.md` 与 `session.py` 的授权序列不得在任务卡未明确授权时改动 |
| 门禁命令表 | Python(在 `.agents/skills/goodjob-career-review/runtime/`):<br>`uv run ruff format --check .`<br>`uv run ruff check .`<br>`uv run mypy .`<br>`uv run pytest -q`<br>前端(在 `.agents/skills/goodjob-career-review/runtime/frontend/`):<br>`npm ci && npm test`(= typecheck + static-gate + 单测 + `build:check` 可复现构建)<br>文档:改动 `docs/` 后跑一次全仓 markdown 相对链接检查,断链为零 |
| 验收纪律继承 | [验收基线 §1](../40-delivery/acceptance-baseline.md) 对本协作同样生效:门禁全绿 ≠ 验收通过;每张卡必须指出它覆盖的 `IMP-*`/`DASH-*`/`SCAN-*` 编号 |
