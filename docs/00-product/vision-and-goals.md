## 问题与机会

长期从业者通常保有多个本地项目，但能即时、准确讲清楚的往往只有最近几个月的工作。旧项目中的技术路线、业务语境、模块边界、实现取舍、测试方式和可迁移知识会随着时间淡化。临近求职时，人工翻仓库既慢又容易把“项目里存在的能力”与“自己实际承担的责任和结果”混在一起。

GoodJob 是一个由 Codex 显式调用的个人职业准备 Skill。它在用户授权且本机可读的工作区中建立可追溯的项目记忆，把分散的项目和模块转化为面向目标岗位的复习材料、简历素材和模拟面试训练。它的核心不是替用户编造经历，而是帮助用户重新理解、组织并能经得起追问地表达已有项目经验。

## 目标用户

首版服务以下同一类个人用户：

- 拥有一个或多个含历史项目的本地工作区，项目可能跨语言、跨仓库、含 Git worktree 或未提交工作。
- 正在准备一个明确岗位，例如应用软件工程师、中间件工程师、架构师、系统工程师，也可能是未预置名称的测试、底层软件等岗位。
- 希望用项目证据重新建立“业务做了什么、技术怎样实现、我能解释什么、还缺什么”的完整叙事。
- 接受 Codex 在本地已授权路径中阅读代码和文档，但不希望这个工具把个人源码和运行状态混入可分发的 Skill 或公开仓库。

GoodJob 不面向团队知识库、招聘方筛选、自动投递或替代候选人的真实经验判断。

## 产品主张

**让本地项目从“想不起细节的代码”变成“针对目标岗位、带证据、能讲清楚的职业能力材料”。**

这个主张由四个原则约束：

1. **证据先于叙事。** 技术和业务结论应能回到项目、模块、文件和状态；资料不足时展示缺口，而不是补写事实。
2. **岗位改变阅读角度，不改变项目事实。** 同一证据图谱可被应用软件、系统或架构岗位用不同优先级解释，但不会为了岗位重写代码事实。
3. **能力叙事与贡献叙事分层。** 所有可读项目代码都可帮助用户形成“我能讲解、我理解、我需要复习”的能力材料；“我实现、我负责、我主导”必须有项目级角色上下文，“我取得结果”还必须同时有可信结果证据。
4. **本地优先且诚实降级。** 工作区原文件是实现事实源；不能读取、不能识别或不应读取的内容必须可见，不以“扫描完成”掩盖遗漏。

## 产品目标

| ID | 目标 | 成功时用户可观察到的结果 |
| --- | --- | --- |
| G-01 | 重建跨项目记忆 | 用户指定一个工作区后，可看到其中可识别项目、工作树和模块的范围清单，以及无法覆盖部分的原因。 |
| G-02 | 形成岗位化理解 | 用户输入任意岗位名称、可选 JD 和可选职级后，能获得该岗位专属的分析维度、项目排序、知识重点和面试问题策略；没有 JD 也不会阻塞。 |
| G-03 | 建立可信叙事 | 用户能从技术点、业务点、模块职责、实现方式、学习收获和知识缺口追溯回证据，并区分项目事实、可讲解能力、个人贡献与结果。 |
| G-04 | 产出可直接使用的求职材料 | 用户获得一份中文岗位准备包、可编辑的简历 Markdown 总稿、STAR 素材、项目讲解和模拟面试题；英文简历与英文问答可按需导出。 |
| G-05 | 形成可持续复习闭环 | 用户刷新项目后不丢失已回答的项目背景或复盘状态，并能记录掌握程度、薄弱点和下次复习日期。 |
| G-06 | 保持本地、可审计和可维护 | 用户的数据不随 Skill 发布或升级丢失；源码不被工具主动上传或复制成完整数据库快照；部分失败不会掩盖为完整结论。 |

## 首版范围

首版包含以下能力，具体可观察契约以 [产品需求](../10-product/product-requirements.md) 为准：

- 通过显式 `$goodjob-career-review` 对话发起，由用户提供工作区路径和一个主岗位；JD 与职级覆盖可选。
- 对指定工作区做本地项目与模块盘点，覆盖 Git 仓库、嵌套仓库、worktree 和可识别的非 Git 项目；以当前可读工作树为实现事实主来源。
- 以统一证据图谱支撑不同岗位的动态 `RoleLens`，而不是为每一种岗位重复扫描或限制岗位枚举。
- 首版深读 TS/TSX、Python、Rust、Dart 和 SQL；其余语言仍生成可用的基础项目档案，而不是被静默丢弃。
- 生成按岗位排序的项目/模块材料，涵盖技术、业务、架构、实现方式、学习要点、知识缺口、简历和面试。
- 仅在业务目标、量化结果或个人角色信息影响材料可信度时，进行一次项目级批量访谈；不要求用户对每个 Claim 逐条确认。
- 保存可编辑 Markdown、离线静态 HTML、不可变准备快照和结构化面试复盘；首次全量扫描后由用户显式刷新。

## 非目标与首版排除项

以下项目不属于首版，后续如需加入必须先更新权威文档与决策记录：

| 类别 | 不做什么 | 原因 |
| --- | --- | --- |
| 贡献归因 | 不从 Git 作者、提交量或文件归属自动断言“我主导/我实现/我取得结果” | 代码归属不能可靠证明个人职责或业务结果。 |
| 虚构与代答 | 不凭代码推断不存在的指标、业务价值、团队角色或个人成果 | 面试材料必须经得起追问。 |
| 多岗位并排比较 | 单次准备运行只聚焦一个主岗位 | 首版先保证一个岗位的材料深度和可解释性。 |
| 语言深读 | 不在首版实现 Go、Java、C#、Swift 等所有语言的深层调用分析 | 先验证通用发现与五种高优先语言适配器。 |
| 自动化监听 | 不监听文件变化、不自动定时扫描、不主动提醒复习 | 用户显式触发 refresh，复习只记录下次日期。 |
| 服务与分发 | 不做常驻本地服务、独立桌面程序或公开 GitHub 发布 | 首版验证 Skill 工作流与离线静态产物。 |
| 代码操作 | 不修改、格式化、构建、测试或提交被扫描工作区的项目 | GoodJob 是只读职业准备工具，不改变用户项目现场。 |
| 外部分析服务 | 不由 GoodJob 主动把源码发送给第三方分析服务 | 本地可读工作区与最小化证据保存是产品边界。 |

## 成功判据

以下是产品层成功判据；具体测试方法由 [验收基线](../40-delivery/acceptance-baseline.md) 定义。

| ID | 对应目标 | 成功判据 |
| --- | --- | --- |
| SC-01 | G-01 | 对真实工作区输出覆盖清单，既列出识别到的项目/模块，也列出跳过和失败的范围。 |
| SC-02 | G-02 | 同一批项目在两个不同岗位的独立准备运行中，产生可解释的不同项目排序、重点和问题策略。 |
| SC-03 | G-03 | 每个关键简历或面试结论都能显示证据来源与状态；无角色信息时不把能力叙事升级为个人贡献事实。 |
| SC-04 | G-04 | 一次成功准备运行产生产品需求规定的完整中文材料，并能从同一快照按需导出英文简历和英文问答。 |
| SC-05 | G-05 | refresh 后用户补充的项目背景、结构化面试复盘和旧快照仍可读取，未变化证据不被当作新项目重新叙述。 |
| SC-06 | G-06 | 审计运行数据后没有完整源码快照或可变个人数据进入 Skill/Git 仓库；离线看板不依赖服务；局部失败在产物中可见。 |

## 核心术语

这些是产品沟通术语。字段、生命周期和状态机以 [证据模型](../20-architecture/evidence-model.md) 为准。

| 术语 | 产品含义 |
| --- | --- |
| 工作区（Workspace） | 用户显式指定、可读取的根路径；GoodJob 在其下发现项目。 |
| 项目（Project） | 一组具有独立工程身份的代码与文档；同一 Git common-dir 的多个工作树属于同一项目。 |
| 工作树（Worktree） | 一个项目在本机的具体目录、分支和 HEAD 上下文，可包含未提交材料。 |
| 模块（Module） | 项目中可独立理解、构建或承担业务/技术职责的子单元，例如应用、包、服务、库、插件或基础设施目录。 |
| 证据（Evidence） | 指向本地项目事实的最小可核验线索，例如文件位置、行/符号范围、哈希、状态和短摘要。 |
| Claim | 从一个或多个证据得出的可呈现结论，例如“项目使用 Rust 服务层”或“该模块实现了任务编排”。 |
| RoleLens | 某一次准备运行针对岗位、JD、职级和项目证据生成的分析镜头，规定关注维度、排序和提问方式。 |
| 能力叙事 | 用户可据项目材料讲解或复习的技术、业务和实现能力，不自动等同于个人职责。 |
| 贡献叙事 | 关于用户实际实现、负责、主导或取得结果的表述，必须带项目级角色信息或可信结果来源。 |
| 项目级批量访谈 | 针对一个项目中多个未决业务、角色或结果缺口集中提问的交互；不是对每个 Claim 逐条确认。 |
| 岗位准备包 | 面向一次主岗位准备运行生成的完整材料集合，包括总览、项目章节、简历、面试和复习内容。 |
